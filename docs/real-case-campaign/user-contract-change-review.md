| 范围 | 核实结果 | 处理与验证 |
|---|---|---|
| 文件名 | 初始目标、授权清单和后续文字直接叠加；改名语法覆盖不足，旧名保留 | f29953d覆盖通用改名及连续改名，不删除同格式的歧义兄弟成果；进一步用经批准的完整交付清单作为正式要求 |

| 确认与审查竞争 | 新Final Review需要能看到已批准的范围变更回执 | scope批准状态与新授权在同一事务中生效，再生成审查快照；审查身份包含正式交付范围证明，预算等无关变更不使该证明漂移 |
| 发布器报告角色调用遗漏 | MC03审查已通过新契约，但Publisher单独调用required_delivery_roles(run)，重新要求已取消报告 | 所有名称/格式/角色要求一次从同一scope读取，移除重复的旧入口；新增从真实审批到对象发布成功的回归，修复前稳定复现WAITING_USER |

不把自然语言里的“只要”“改成”直接当作撤销旧契约的权限。完整清单改动必须经用户确认；初始目标仍作为内容/结构/方法验收的依据，不能借交付改名丢掉画面、时序、可编辑结构或技术质量要求。继承自父Run但尚未确认的范围与本Run已批准的交付清单分别处理。

## 其他可变项的检查

| 用户可修改项 | 当前权威来源及边界 | 本次结论 |
|---|---|---|
| 时长、尺寸、帧率、裁剪、字幕/音频参数 | 当前Task spec/parameters/acceptance与不可变revision；旧候选清空，实际文件独立验收 | 未发现交付清单式的旧值并集规则；追加MC03真实组合变更，验证640×360/24fps而不是旧960×540/30fps |
| 素材替换与新增 | 冻结asset digest、授权版本、输入绑定、安全点；未授权素材先确认 | 保留现有归属/版本验证；换素材不等于直接撤销已经授予旧Attempt的权限 |
| 处理方法 | 用户明确修改、允许的Operation/Profile、当前执行来源与独立审查 | 不把Reviewer建议当作用户授权；方法修改不因交付清单变化自动获准；保留method_use校验 |
| 验收标准 | 受用户输入作用域约束的新Task revision及新Review identity | 不复用旧标准下的审查；技术完整性检查不能由用户或模型豁免 |
| 输出角色、Task类型、依赖 | 类型化Proposal、显式replacement、后代闭包与冻结字段校验 | 保留显式替换与依赖检查；不能仅改输出清单就隐藏失败工作或改变Task身份 |
| 主成果 | 当前最终Review的primary必须属于其已检查的deliverables，发布器复核同一回执 | 没有从旧页面选择恢复primary的旁路；变更后按当前审查与交付范围选定 |
| 能力/权限/预算 | 新授权版本、能力目录、原始已用及未知预留账本 | 交付调整不能扩大未批准能力，也不能清零用量；已确认清单不能直接清空以跳过交付 |
| 顶层目标、完成后的新要求 | 独立Run与明确授权/方案确认；旧Run/旧成果保留 | 不回写已经发布的契约；Manager只读消息与业务变更分别处理 |

这些结论区分代码/确定性回归与模型语义判断，不宣称模型永不误解自然语言。没有明确字段身份、多个同格式输出含义不清时仍须澄清，不能猜测删除其他成果。
