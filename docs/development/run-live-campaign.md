# 真机测试与审查规范

适用于本分支的真机 case 设计、部署后执行、失败归因、修复复测和跨窗口审查。环境和发布门禁见[开发与测试](../development.md)，用例目标见[审查矩阵](../real-case-campaign/dynamic-case-review.md)。本规范不代表启动新轮次或解除现有暂停的指令。

## 入口和执行前核对

- `docs/real-case-campaign/dynamic-cases.json`：case 清单；当前 126 条，数量变化时同步矩阵和报告。
- `tests/campaign_suite.py`、`campaign_dynamic_browser.cjs`、`campaign_dynamic_probe.py`：编排、真实页面和内部状态审查。
- `.cluster/release.json`、`.cluster/verification/`：实际部署和冻结代码门禁；不得以工作区 HEAD 代替部署摘要。
- `.cluster/campaigns/dynamic-plan/`：轮次和尝试证据；`pause-new-cases` 为既有暂停控制。检查运行进程和实际记录，不能仅凭文件名推断已停止。

开始前核对冻结源码、case manifest、驱动及部署摘要，确认目标是独立实例，素材和证据位于 `/data2/wujing03`。正在进行的轮次不能静默更换代码、模型或验收标准。修复后建立新的版本绑定并保留首次失败；测试前已存在的暂停不得自行解除。

普通case并发不得超过驱动和部署的双重上限；增加浏览器jobs时同步核对执行节点沙箱数、CPU/内存准入、用户并发及Provider并发组。并发增加不适用于全局故障注入和独占资源case。容量变更需要新源码/配置摘要、门禁、部署和source lock，不能在进行中的冻结轮次里静默切换。

本轮约定的业务沙盒模型为 `claude-4.6-sonnet`，推理强度 `high`。2026-11-07 用户追加要求：后续批次将原 `claude-sonnet-5-5` 的 Manager、诊断、任务审查与最终审查角色改为已登记的 `deepseek-v4.1-flash`（`deepseek41` 预设、high），仍使用 `structured-profile-v4`；Editing Implementer 保持原已选模型。旧 Claude 批次保留，代码修复与模型切换一同发生时，不将差异全部归因于模型。驱动提交前核对 `model_protocol_policy=plan_draft_v1_strict_preferred`，创建后核对 Run 的 `model_configuration`，保存实际配置摘要。每个 PLAN 还必须核对唯一 PlanDraft 的 snapshot/graph/authorization/input cutoff 绑定、revision 及 COMMITTED/REJECTED/EXPIRED 终态。服务能力策略、Run 冻结配置、PlanDraft 和每次请求实际 strict/回退是不同证据；只核对一个字段不能证明全部生效。

还需核对每个角色冻结的`response_transport`：控制角色为`buffered`，Editing Implementer为`stream`。日志中的请求模型、上游实际模型和传输方式必须一致解释；配置Claude而上游回显其他路由时单列。性能报告至少包含各角色模型调用数、平均/最大总耗时和Publisher耗时，不能把整个case耗时笼统归给媒体处理。

改变模型默认值不能追溯修改已有 Run 或重标历史结果。预算边界用例保留设计中的低额度，不能为了让模型执行而放宽；模型选择部署 smoke 不替代正式媒体 case。

## 每个 case 的审查

1. 先列明业务目标、必测状态边界、预期恢复和独立验收方法，再执行。调整 case 先更新矩阵；通用修复不得增加按 case ID 分支的产品逻辑。
2. 核对 Run、Task/Control Job、revision、Attempt/Lease、输入 sequence、排空集合、Provider 外部句柄与预算。旧结果不得复活，原外部任务不得重复提交。
3. 保存关联日志和可观测性、数据库、Redis、BOSS、候选/交付哈希、浏览器与清理证据。某一来源不适用时注明原因；来源缺失时标记审查缺口，不写成已通过。
4. 浏览器审查实际进度、等待、输入反馈、控制、候选/交付和错误提示；截图只证明截图时刻，不能替代交互或媒体播放验证。
5. 模型协议问题检查真实公开回复、提示/Schema 一致性、证据引用、阶段和纠错预算。私有推理和凭据不写入日志；受控原始请求证据不能直接复制到公开报告。

## 分类与复测

| 分类 | 结案要求 |
| --- | --- |
| 成功 | 业务验收、必测边界和内部/浏览器审查均满足；未审查时单列待审查 |
| 程序错误 | 提供触发条件、证据和通用根因；修复后先复测失败 case，再推进约定范围的完整回归 |
| 非程序失败，程序处理正确 | 证明是模型或外部依赖原因，且有界纠错、恢复、授权、停止和清理符合设计；可计程序正确性通过，但不改称业务成功 |
| 待归因 | 证据不足或根因未确认；不得提前归到非程序失败 |

必测边界未触发、用户停止、未执行、正在运行和证据缺失分别报告。即使已确认某次是外部依赖失败，必测边界未覆盖也仍需复测，不能用“非程序失败可通过”豁免覆盖。

复测应服务于程序缺陷修复、必测边界覆盖或有明确依据的通用提示改进。若 Schema、权限、确定性校验、拒绝、停止和清理均正确，重复失败仅来自模型波动或外部依赖，则保留原始结果并结案；不得为了压低数字无限复跑、增加 case 特例或持续膨胀提示词。最终报告分别给出业务成功率、程序正确性和未覆盖边界。

非法 JSON、错误 evidence ref 或反复内容拒绝不天然属于模型问题。先排除提示与 Schema 冲突、工具契约错误、截断、证据投影遗漏、错误反馈不足、预留预算不合理等工程诱因。HTTP 200 不证明 strict 生效，接口 502 不证明 strict 不支持。

## 进度、交接与完成标准

活动测试期间按用户约定每 2 分钟汇报：总数、已启动、成功、非程序失败、程序失败、待归因、运行中、尚未执行；注明轮次、按 case 最新一次尝试去重的口径，并单列用户停止等额外状态，保证可以核对总数。重试次数和 case 数量分开，首次失败保留在历史中。

每个已启动但未终态的 case 单独一行：ID、阶段、耗时、最近有效进展、是否符合设计预期、异常原因或下一检查点。重复无进展、重复付费请求或确定性程序错误立即报告，不等待定时报表。协议实验另按模型和协议报告平均时间，说明失败、超时、排队与用户停止的计入方式。

多窗口协作先明确负责执行和修改的一方，其他窗口默认只读审查，避免同时部署、重启、修改相同文件或创建重复轮次。交接须包含已部署版本、暂停状态、活动 case、未解决缺陷及证据路径。

驱动收到SIGINT/SIGTERM时必须先阻止新case，向所有活动Run提交cancel并进入既有finally审计与项目清理；第二次强制信号才允许直接退出。仅停止父进程而留下后台Run不算停止成功。

最终报告绑定轮次和版本，包含逐例结果、实际配置、必测边界、归因、首次失败与复测、内部/浏览器证据、清理及未验证限制。代码检查、模型回复实验、预算链路测试、部署 smoke 和完整媒体 case 验收分别列出，不能互相替代。仅修改本规范时检查链接、命令和实现一致性，无需启动付费测试。
