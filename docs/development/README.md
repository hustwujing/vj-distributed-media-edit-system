## 阅读与维护边界

先按实际修改选择主说明，再读取被影响机制的专项；引用其他主题用于定位，不要求递归读完所有文档。HTTP 请求的并发与耗时隔离归 API，能力注册归 operation，步骤契约与验收归工作流，方案确认归 Agent，对执行归属和持久化的修改归分布式，供应商协议归外部服务，指标与账本归可观测性，浏览器呈现归前端。

跨主题只保留调用方必须遵守的边界，完整实现步骤、字段语义和测试细节集中在负责该机制的说明，通过链接复用。通用环境、隔离测试、发布检查及仅文档改动的验证方式统一维护在[开发与测试](../development.md)；各篇命令是定向示例，不是每次任务都需执行的固定清单。

开发规则描述必须保持的约束，不等于每条都已由同一个 API 自动保证。发现代码与说明不一致时核实校验位置和实际行为：过时描述应修正，实现缺口应明确记录，不能通过放宽权限或复用历史验收宣称已经满足。历史设计中的实施计划和当时授权不构成本次任务的部署授权。

## 新增主题

每个主题使用独立 Markdown 文件，并补充上表。说明应包含：

1. 适用任务和边界。
2. 应先阅读的接口、代码和测试入口。
3. 按实际开发顺序组织的步骤与关键约束。
4. 验证方式、完成标准及文档同步要求。

代码模板和协议已有专门文档时直接引用，避免复制后产生多份不一致的规范。历史调查、单次发布数据和机器凭证不放入开发规则。
