# 程序正确性审查原则

用户明确的审查原则，记录于 2026-11-01。

主要判断程序状态、权限、数据与恢复机制是否正确。模型偶尔选错工具、命令失败或首次产物未达质量标准，都可以是正常的异常输入；应检查系统是否发现、隔离、恢复并如实展示，而非要求模型每次都一次成功。

## 通用检查项

- 输入、方案和工作文件的逻辑内容没有变化时，缓存落地、节点切换和检查点保存不应让方案失效；实际内容变化仍须使旧确认失效。
- 工具退出、模型回复结束、技术检查通过、质量批准和最终交付是不同状态，不相互冒充。
- 失败或质量不合格有可追溯记录，重试有界；修复保留验收标准、版本、权限与输入约束。
- 下游只能使用已批准的正确上游修订及哈希；未受影响的成功步骤应复用，旧候选不得混入最终交付。
- 用户决策绑定任务、步骤和修订；需要确认时暂停，确认前不得抢跑下游。等待用户期间不应持续产生计算调用或占用执行资源。
- 异常和乱序事件不能造成状态回退、假成功、无限转圈、重复提交或重复计数。
- 用量按任务、明确关联的需求、项目分别核对；原始回执、可计算值与未知值分开说明。
- 完成后任务、工作流、待办、租约和清理状态一致，输入与产物有持久化记录。

## 如何处理发现

优先修复可跨任务重现的程序缺陷。回归测试按不变量和状态转换组织，使用多种文件名、内容、存储状态与执行顺序；审计样例提供证据，不成为业务代码的特殊分支。

正常被捕获并恢复的模型错误，记录为鲁棒性证据。性能、文案和统计范围的改进建议，与真正的数据错误或状态机缺陷分开列明。
