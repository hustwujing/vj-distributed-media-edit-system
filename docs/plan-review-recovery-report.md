# 方案审核与 Jev 上下文修复验收

完成时间：2026-11-03 11:57:11 CST。部署版本 `104943e9e307`。

修复了方案已生成却因分类不确定无法确认、确认后重复讨论的问题，并审查了全部 Jev 入口。实现与边界见[设计说明](plan-review-recovery.md)。没有为单个项目、转写任务或提示词设置专用路由。

| 判定 | 上下文问题 | 修复 |
| --- | --- | --- |
| 方案就绪 | 只有视频元信息，没有已保存转写/工作文件；确认跟进缺原方案 | 加入有界保存文件证据和历史；不确定独立复核一次，缺信息给具体项 |
| 自然语言确认 | 只找 ready 方案，未就绪确认掉回讨论 | 关联原方案，增加原需求/审核状态/所选目标；不生效的确认不自动执行，重新检查后须再次确认 |
| 任务控制与重新规划 | 仅消息与 task_status，缺方案/步骤/待回答问题 | 添加当前任务精简上下文与语义版本绑定，返回后复核；不把选项回答或历史文字当控制授权 |

## 验证结果

- 冻结版本 Python：706/706，0 跳过；前端：44/44。
- 隔离真实 Chromium、双 API、PostgreSQL、Redis：10 项通过，覆盖阻塞提示、原方案重试、刷新、窄屏、再次确认、重复与越权拒绝。分类器采用协议夹具，业务授权走真实服务逻辑。
- 真实方案服务：5 组通过，包括原不确定输入的独立复核、保存文件证据、确认跟进的历史方案、确实缺素材与问候；使用独立数据库，不写用户业务状态。
- 真实控制服务：8 种表达，各做有/无上下文对照，共16次。查询、恢复、局部重规划和取消被正确识别；选项回答、假设和否定均未执行错误操作。一条暂停表达在两种输入下均低于95%门槛，程序保持任务不变；这是安全处理，不计为正确识别暂停。
- 部署后真实浏览器：载入独立示例、由真实 Agent 生成方案，确认按钮显示并刷新保留；发送自然语言确认后进入 execute，产出并下载文字稿。模型用量、审核记录、清理和主成果另附诊断证据。
- 部署后真实重新规划：从浏览器输入出发，实际 Jev 判断否定/假设与修改要求，旧任务取消、新方案再次确认、已完成成果复用及最终文件检查均通过。
- 用户原项目通过现有重新检查方法重审最新方案；没有直接写 ready，也没有消费历史确认或开始执行。结果见结构化证据。

## 运行边界

Jev 置信度不是校准正确率，单次分数不能证明普遍可靠。补齐证据后本例 ready 约99.6%，补齐历史后跟进轮约99.8%；原输入另次复查约83.6%，仍由有界独立复核接手。数字属于当次实测，不作为新固定阈值。

明确按钮和固定口令仍走确定性路径；自然语言控制不增加自动二次模型操作。部署后R17还出现一次模型语义偏差：“不要重新做，保持当前方案”被Jev判为resume（约96.7%）。原任务仍处于人工验收停点，服务端恢复门禁返回409，任务没有改变。这验证的是程序防护，不能计为Jev正确理解了否定表达。

模型返回期间方案、步骤修订或待决问题改变时返回409，不应用过期解释。方案检查通过只允许确认，绝不等于授权执行。

首次源码目录观测定向测试有3项降权读取权限失败；正式冻结运行包使用既有权限准备后完成全量验证。静态 review 还发现并修正了非轻量确认逻辑的分派位置，补充 Claude/DeepSeek 实际调度回归；未完成的旧冻结验证已中止，未用于发布。

本轮未重跑历史77条完整媒体集合。真实服务验证范围、低置信度安全处理和全部检查结果见[结构化证据](plan-review-recovery-evidence.json)。部署后文字稿测试最初因驱动额外限定txt格式而误报失败；实际已确认和交付均为Markdown。检查器修正后复查同一文件，无重复执行，并保留原失败记录。原始模型输入、浏览器Cookie和凭据保存在私有测试目录，不随报告提交。
