# 非程序错误的含义与共性原因

本分析对应已完成全部97条及逐例审查的 `9446e2e10695`，归档为`.cluster/campaigns/dynamic-plan/report-9446e2e10695.json`。该轮72条用例通过、25条非程序失败、用例审查未留程序错误。随后main增量审查在额外沙盒复现中发现F42/F43，两项正在同步验证；不能将本轮用例结论扩大为程序所有路径都无缺陷。新版本的最新数量以[完整报告](dynamic-test-report.md)为准。

“非程序错误（程序处理正确）”表示已核对该次失败的程序应对：保留真实错误、执行冻结的验收与预算、暂停/取消、不误交付，以及数据库、账本、日志、观测、缓存、BOSS和清理状态一致。它不表示模型行为合理、任务已完成，或当前产品设计无需改进。

## 为什么一次问题会变成整条任务停止

以上是失败触发原因；另一个维度是失败后的处置。逐条读取该轮正式状态：

| 最终暂停原因 | 数量 | 用例 |
| --- | ---: | --- |
| diagnosis_ready：诊断完成后停止 | 12 | S21、C02、C07、C09、C10、C11、C12、C14、C16、C18、C21、C22 |
| task_review_rejected：步骤内容拒绝后停止 | 6 | S09、S20、S29、C04、C20、C30 |
| budget_exhausted：单Task审查预算耗尽 | 7 | C01、C03、C13、C15、C17、C19、C29 |

`workflow_orchestrator.accept_diagnosis()`目前保存诊断后设为paused/diagnosis_ready；步骤内容拒绝也直接暂停。相比之下，最终Review明确reject会解除sealed并将反馈送回Manager规划。这几条恢复路径并不对称。

设计文档第12.2节要求“需要新增任务时返回Manager重新规划”，第13节要求不合格结果进入受控修复、重新规划或用户决策。当前诊断完成并未连接到按诊断决定是否重新规划的完整流程。这是需要补齐的实现与设计问题，不能因为暂停、账本和清理正常，就声称自动修复闭环已经完成。

因此“非程序错误”标签仅描述当次异常处理与状态完整性，并不证明根因完全在模型，也不证明实现已完整满足设计。接下来须区分可在原授权、原目标和原标准内修复的情况，以及必须征求新授权的情况；不应将全部失败一律暂停，也不能一律自动重试。修复需要明确旧失败节点与新修复节点、下游依赖及最终必需任务的关系，保持失败历史和禁止错误交付。

该轮7个轮数耗尽用例的工作流总Token预算均为200万，暂停时仍余约127万～184万Token，未有未结算预留。限制它们的是单个审查Task的12轮上限，不是工作流总Token不足。统计见`.cluster/campaigns/dynamic-plan/failure-recovery-analysis-9446.json`。

## 已确认的说明缺口

部署冻结的`references/dynamic-operations.md`列出`mute`，但未明确“静音仍保留音轨”；标题`background`也未标注布尔类型。该信息缺口与重复误用相符，是工程侧需要承担的潜在诱因。现有证据尚不能量化其因果贡献，也不能承诺单独补充说明就消除失败。

改进应明确操作输出与验收字段语义，并用相同任务和固定比较口径验证。不得把`audio=false`偷换成“音频采样为零”，也不得放宽既有冻结验收来改写历史结果。本次正在执行的冻结版本仍按原始契约完成覆盖；尚未实施的改进不能写成已修复。

### 复杂媒体命令根因与通用修复

留存的24段真实输入已完成隔离复现，证据为`.cluster/c22-rootcause-report.json`。根因不是视频尺寸、帧率或CRF错误，而是FFmpeg选项作用域与任务线程上限共同造成的资源耗尽：

- 原命令同时打开24路H.264输入，只在第一个`-i`前放置一次`-threads 2`，其余解码器仍自动创建线程。
- 在`TasksMax=128`下，原命令稳定复现`Resource temporarily unavailable`；原现场在libx264打开时暴露，复现中在第9路解码器初始化时暴露，均属于线程/任务额度耗尽。`oom_kill=0`与此一致。
- 只限制输出编码线程仍失败；逐输入限制解码线程虽成功，但FFmpeg线程峰值127，仍贴近128上限；再限制输出编码线程峰值118，仍不理想。
- 对兼容片段使用concat demuxer后，线程峰值降为26；在`TasksMax=64`下仍成功。输出为48秒、640×360、25fps、H.264/AAC、1200帧；24段中点与各源段最大MAE约1.055，循环音乐相关性0.999989、增益0.999278。

通用修复方案：声明式媒体编译器先探测片段兼容性；兼容片段使用concat demuxer顺序读取；不兼容片段按有界独立任务逐段规范化、保存检查点，再顺序拼接。所有输入解码线程和输出编码线程分别显式限制，并在准入阶段估算TasksMax、内存、临时磁盘和输入规模。禁止模型直接生成任意规模的单进程多输入filter graph。执行记录保存规范化命令摘要、完整有界stderr、FFmpeg/编码器版本、输入清单、线程峰值、cgroup限制及退出原因。

- 生产代码、Prompt路由和验收器不得读取case ID、测试标题、测试目录或匹配完整测试提示词来选择行为。
- 修复必须由类型化目标、注册operation元数据、授权、错误码、实际产物和证据驱动。
- 单元测试使用参数化素材与随机名称；协议测试至少覆盖同一规则的多个媒体类型/尺寸/声道/分支结构。
- 真机case只是端到端回归层。仅修改campaign驱动、降低预期或为固定文件名增加分支，不计为产品修复。
- 每项修复同时验证正例和反例，防止为了减少拒绝而放宽错误交付。
