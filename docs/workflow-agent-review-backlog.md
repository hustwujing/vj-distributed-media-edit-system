## 现有基础与缺口

当前已有步骤持久化、依赖执行、执行异常检查、基本产物检查、显式 acceptance 条件、有限安全重试、预设 repairs、人工质量确认和最终 Agent 验收。

主要缺口是：中途步骤遇到问题时，尚无通用的自动唤回 Agent、理解需求与产物、诊断原因、修改方案并续跑的闭环。仅检查文件有效，不能保证内容符合用户意图；未覆盖的语义错误可能传递到后续步骤。

## 建议方向

统一流程：执行步骤 → 确定性检查 → 按需 Agent 内容验收 → 通过后继续；不通过则诊断、修复并重新验收。

- 确定性操作优先使用程序检查，不要求每一步调用模型。
- 内容验收结合原始需求、已确认方案、步骤输入、实际产物和验收标准。
- 区分临时故障、实现错误、需求含糊和不可恢复问题，分别采用有限重试、修改脚本或参数、向用户澄清、保留成果并暂停。
- 保留已完成且仍有效的结果；修复时识别并重新执行受影响的下游步骤，避免旧结果与新输入混用。
- 修复遵守原有授权、外部调用约束、次数和资源预算，避免无限循环与重复生成。
- 状态、验收结论、诊断、修复版本与产物应持久化，支持重启恢复和审计。
- 用户侧能看到正在验收、问题原因、修复进度，以及需要用户决策的事项。

通用的是“检查—诊断—修复—再检查”机制；具体任务仍需适用的验收标准。不能承诺自动识别或修复所有错误。

## 后续实施前需细化

步骤级 Agent 调度与权限、验收上下文契约、修复与下游失效规则、重启及幂等处理、预算边界、进度展示和故障场景验证。

## 用户认可的分阶段推进方案

用户进一步明确：workflow 本来就是 Agent 编写的，验收条件与异常策略也应由 Agent 自动显式填写，而不是要求用户手动配置。用户已认可以下方案，之后授权实施。

### 第一阶段：提交时自动补齐执行、验收与异常策略

- 用户表达目标；Agent 根据实际素材、原始需求和已确认方案，为每个步骤生成输入、操作、依赖、预期输出、验收方法和失败处理。
- 可量化要求优先写入现有 acceptance，例如尺寸、时长范围、音视频轨道；框架未内置但可以程序判断的要求，可编写检查脚本，以失败退出阻断后续执行。
- Agent 明确哪些操作可以安全重试，必要时提前提供 repairs 备用命令；无法自动判断的内容安排质量确认点。
- 同时加强 Agent 编写规则与服务端提交校验。提交不完整时，返回具体缺项，让 Agent 补齐后再提交；不能只依赖提示词，也不能仅检查字段非空。
- 不强制每一步必须有备用方案；允许明确选择失败后暂停。不能为了满足校验虚构修复策略或机械设置 retry_safe。
- 检查条件存在不等于覆盖全部用户意图；需要关注条件与需求、产物之间的对应关系。
- 现有 acceptance、repairs 可为空；强化提交校验属于待实现改动，不应描述为已具备。

### 第二阶段：运行中的 Agent 验收与诊断续跑

在第一阶段基础上，补齐前述步骤级 Agent 内容验收、问题诊断、有限修复和重新验收机制，处理必须理解内容才能判断或提交时未预料到的问题。

必须区分：Agent 提前写验收计划，并不等于调度器运行中会调用 Agent 验收。当前 review 条件会等待用户确认，不会自动唤醒 Agent 看结果并修复。


## 已实施

- 新提交计划必须显式填写 goal、acceptance、on_failure；基础检查需 basic_reason，提供不落库的 validate 操作。
- 程序规则拒绝不会执行的文字条件与无效字段组合；预设修复按错误代码匹配。
- 失败阶段、退出码、脱敏日志摘要、输入版本与尝试次数持久化为诊断记录。
- 同一执行轮可进入步骤 Agent 验收、诊断、最终验收；真实低权限网关与宿主共用接口逻辑，并绑定验收请求 ID。
- 验收 Agent 的既有工作区只读，新修复脚本写入独立目录并随检查点保存；无权直接调用图片或转写工具。
- 结构化结论须提供产物证据，服务端复验文件哈希和技术条件后放行。自动修复仅能更改本地 argv，保留验收契约、依赖和执行策略；受影响结果按版本失效。
- 最终交付须明确选择通过验收的文件，不能仅因 Agent 正常结束而标记成功。最终用户问题挂到具体候选步骤，提供确认和反馈入口。
- 验收中断可有限恢复，未应用结论丢弃；取消、版本变化和预算到期优先，重复提交/应用不会重复完成业务步骤。
- 增加 workflow.image/remove_bg 固定本地抠图，复用 GPU 分配与隔离执行，支持步骤级恢复和前景/蒙版检查点。
- 前端展示程序验收、Agent 验收、诊断、修复次数和最近诊断；明确最终交付与中间产物。

运行协议见 [后台工作流](../references/durable-workflows.md) 和 [Agent 验收协议](../references/workflow-review.md)。

## 验证范围与后续边界

验证包含真实 Linux 沙箱、低权限 HTTP 网关、脚本检查点、真实文件验收，以及模拟模型结论下的状态机、失败、重启、取消与修复测试。未调用真实生成服务或 GPU 抠图模型，也未通过真实模型会话评价语义判断准确率。

本次验证结果：Python 全量 187 项通过；补齐最终用户反馈入口后，相关 60 项回归通过；前端状态与成果排序 11 项通过。已重建本地沙箱工具清单，新增运行文件已按现有规则补齐服务账号读取权限。

外部提交结果未知仍须暂停核实；不会因自动诊断而获得重复外部生成权限。自动修复当前限于本地执行命令，改变用户验收标准或扩大外部调用范围仍需明确决策。程序验收不能证明验收条件完整覆盖用户意图，内容判断也不能保证识别所有错误。

## 待实现：多阶段任务的图片操作统一编排

用户于 2026-10-31 明确认可并要求先记录以下规则，本次仅记录，暂不实施：

> 已确认的多阶段任务中，只要图片操作属于工作流支持范围，就应作为工作流步骤提交；直接图片工具用于独立、短小的单次处理。

- 当前已向 Agent 说明工作流支持 generate、decompose、remove_bg，并实现对应后端；直接图片工具仍保留。尚未强制约束 Agent 的路径选择，也没有自动把直接调用转换为工作流节点。
- 后续需把上述规则写入 Agent 编排指令和能力说明，并设计直接工具入口的校验或引导，避免仅依赖模型自觉选择。
- 多阶段任务应将支持的图片操作及其后续依赖一起持久化；例如“抠图 → 合成 → 检查”应把抠图纳入同一工作流，不应先在普通执行轮同步抠图。
- 实施前需明确如何根据已确认计划识别多阶段任务，以及独立短任务的适用边界；不能只凭是否已有 workflow 记录判断，因为直接调用可能发生在工作流提交前。
- 保留独立短任务的直接工具入口。此事项不是删除 remove_bg 工具，也不表示该约束已经上线。

## 待优化：耗时操作统一编排与资源声明

用户于 2026-10-31 认可将优化范围从图片操作扩大到项目内各类 CPU、GPU、内存、磁盘和网络密集操作，并要求先记录；本次不实施。

### 范围与原则

- 盘点视频合成与转码、抽帧与时间线、媒体检查、图片批处理、分割、边缘精修、OCR、转写、生成、分层、选区重绘及擦除等已有能力，逐项确认执行方式与恢复边界。
- FFmpeg、Pillow 等通用本地处理继续复用 local，不必为每个动作新增步骤类型。
- 需要特殊 GPU/模型环境或外部服务的操作，通过受控执行器接入工作流；不让普通 local 脚本绕过任务管理直接调用外部服务。
- 多阶段任务中的耗时处理和外部调用优先持久化编排；已有受控能力通过对应执行器调用，独立短操作保留直接入口。与前一项图片编排规则统一设计。

### 统一能力契约

由服务端登记操作的输入参数、输出契约、资源需求、执行方式、超时、取消、重试、恢复、授权、进度与验收方式。Agent 根据能力契约选择操作、组织依赖并填写业务参数；资源权限和恢复规则由服务端控制，不能完全依赖 Agent 自报。

- 区分同步本地计算与异步外部任务，分别处理计算进程、外部任务 ID 和查询等待。
- 按实际资源容量调度，补充 CPU、GPU、内存、磁盘及外部服务并发约束，避免仅按任务数量限制并发。
- 区分安全重跑、查询已有任务、提交结果不确定等恢复路径，避免重复外部提交或重复计费。
- 统一取消与资源回收，明确哪些取消可确认、哪些上游可能仍在运行。
- 分开展示“等待资源”“正在计算”“等待外部结果”“接收结果”“验收”等阶段；没有真实进度时不虚构百分比。

### 建议推进顺序

1. 盘点已有能力，建立服务端能力登记与统一执行协议，同步明确多阶段任务和独立短任务的入口规则。
2. 整理已有本地图片执行器、外部图片适配器和受限代理，保留现有隔离、租约、预算与检查点能力。
3. 按能力逐步接入转写、分割、精修、OCR 等操作，并声明各自真实的恢复与取消边界。
4. 补齐按资源调度、外部调用记录、前端阶段展示以及重启、取消、重复提交和防绕过验证。

避免每增加一个工具就重新实现整套任务生命周期；不要求先引入独立微服务，执行器可以先作为项目内后端模块实现。

以上均为后续优化方向，不表示所有列举操作已支持工作流，也不表示已实现按资源统一调度。

### 2026-10-31 补充：受控执行器的具体完善点

用户要求根据执行器实现讨论刷新 TODO。本节仅完善设计与验收目标，不授权本轮继续修改实现。

#### 服务端能力登记

- [ ] 为每个能力登记操作 ID、参数校验、素材归属检查、输出契约、固定程序入口或服务适配器、模型/环境版本、资源需求、执行期限、恢复与取消策略。
- [ ] Agent 只选择操作、业务参数与依赖；环境路径、模型权重路径、GPU 分配、服务地址和密钥由后端决定。资源申请由服务端根据参数和配置校验，不能信任 Agent 任意指定资源或权限。
- [ ] 对 Agent 暴露的能力说明与服务端实际允许列表保持一致，减少文档宣称支持、提交却拒绝的偏差。
- [ ] 统一 direct/manual/workflow 的底层能力实现，同时保持各入口的任务归属和授权边界；不要通过创建嵌套 manual 任务来替代工作流步骤生命周期。

#### 本地模型执行器

- [ ] 抽取固定模型执行公共流程：校验租约和预算 → 申请资源 → 启动隔离进程 → 输出检查与检查点 → 回收资源。
- [ ] 将当前共享的图片模型环境挂载清单逐步缩小为按能力配置；仅提供该能力需要的环境、模型目录和已分配 GPU 设备。
- [ ] 输入只读、每次尝试独立输出目录；超时、取消或租约失效时终止对应执行范围内的进程，确认清理后再释放 GPU，清理不确定时保持隔离。
- [ ] 明确步骤级恢复语义：已完成结果复用，未完成计算仅在允许时重跑，不承诺 GPU 推理中间状态续算。
- [ ] 统一资源等待与运行时限、尝试次数和累计预算；重启或更换执行器不能重置配额。

#### 外部服务适配与调用记录

- [ ] 异步服务统一提供 submit/poll/collect/cancel 语义；同步服务明确单次请求生命周期，不能假设所有上游都有可查询任务 ID 或取消接口。
- [ ] 调用顺序固定为先保存提交意图，再请求上游，收到任务 ID 后持久化；之后查询、下载和取消均绑定该任务。
- [ ] 使用工作流、步骤、修订号等生成稳定请求标识；只有上游幂等协议实际得到确认时才能据此恢复提交。仅发送 Idempotency-Key 不代表上游保证幂等。
- [ ] 对“上游已接单、本地未保存 ID 就中断”保持明确的提交未知状态；无可靠找回机制时暂停核实，不自动重复提交。
- [ ] 下载产物也受任务授权、大小与格式限制，记录取消是否确认，不把本地停止等同于上游已停止。
- [ ] 统一记录所属任务/步骤/修订/尝试、服务商、请求标识、任务 ID、提交确认状态、可获得的用量及费用信息和授权依据。
- [ ] 明确现有调用配额与任务预算不等于完整金额计费系统；未取得费用信息时保持未知，不将网络超时解释为未计费。

#### 防止普通 local 绕过执行器

已有基础：local 使用独立网络命名空间，没有可用模型服务网关，不提供服务凭据，也不挂载专用 GPU 设备及模型环境。继续复用这些实际隔离措施，不把提示词作为唯一约束。

- [ ] 确保统一能力接入后，普通 local 仍不能直接访问内外部服务、继承 Agent 的有效网关或获取受控模型环境。
- [ ] 固定工具确需访问服务时，代理只允许已登记目标、操作、素材和任务 ID，不提供通用 HTTP 代理或任意命令入口。
- [ ] 在多阶段任务的直接工具入口增加校验或引导；服务端识别依据应来自已确认计划，不能只看 workflow 是否已经创建。

#### 验收与故障测试目标

- [ ] 用 Python requests、curl 或自行启动代理的 local 脚本，均不能获得宿主网络或调用受控服务；不能读取密钥或使用未分配的 GPU。
- [ ] 外部提交前后各中断窗口、重复请求、已有任务查询恢复、部分下载失败和取消未确认均有明确状态，不能重复计费性提交。
- [ ] GPU 等待、执行超时、进程残留、租约接管、资源隔离和结果检查点复用有集成测试。
- [ ] 前端准确区分等待资源、执行、等待外部结果、收取结果、验收和取消确认，并显示必要的恢复或用户决策原因。
- [ ] 对新接入的能力补真实环境验证；模拟执行器测试不能替代真实 GPU 模型或上游服务协议验证，分别记录验证范围。

- [ ] 接入外部图生视频能力，复用提交意图、任务 ID、查询、收取结果、取消、配额与恢复协议。

- [ ] 明确人物风格、画幅、图标尺寸/边距/显示时段、音频需求和外部调用范围，将合理默认值纳入方案；不要把每个参数都变成用户必须填写的配置。
- [ ] 设计可用于 local 和外部模型步骤的统一产物引用，例如“步骤 ID + 输出角色”；角色名 primary_image 等仅为设计示意，尚不是当前提交协议。
- [ ] 引用由服务端解析：校验项目归属、声明依赖、已验收状态、输出类型、步骤修订与文件哈希，绑定本次实际消费版本；不依赖数组顺序、模糊文件名或 Agent 任意提供的 URL。
- [ ] 明确多产物选择规则：主图、蒙版、预览图、分层文件等应有稳定角色；多个候选无法唯一选择时不能默默取第一张。
- [ ] 由适配器完成参考图上传或受控引用，登记上游素材句柄及有效期（若服务需要）；任务重启不能因重传素材而隐式重复提交生成任务。

#### 依赖与验收安排

目标业务步骤：A 生成人物图；B 使用 A 的已验收主图生成视频；C 上传图标抠图；D 使用 B 视频和 C 前景合成；E 检查成片。最终 Agent 验收选择明确的交付文件。

- [ ] A 验收通过才允许提交 B，避免将不合格参考图传入更耗时或收费的视频生成。
- [ ] C 与人物生成链路无数据依赖，允许按资源调度安排；D 必须等待 B 与 C 验收通过。依赖独立不等于已支持任意并行，需明确当前调度约束与后续并发策略。
- [ ] 人物图检查格式、尺寸和描述符合程度；视频检查参考人物一致性、沙滩场景、奔跑动作及明显异常。
- [ ] 视频内容验收准备代表帧与关键动作片段，记录抽样覆盖范围；不能只凭封面断言持续奔跑或全片无异常。
- [ ] 图标检查透明背景、主体完整性与边缘；最终成片重新检查布局、遮挡、时长、分辨率、轨道及解码，不沿用合成前的验收结果。
- [ ] 明确 15 秒的帧级容差和最终输出规则；检查报告、预览帧与成片版本绑定。
- [ ] 默认按已确认方案由 Agent 验收；用户明确要求挑选人物或有主观选择时再安排用户确认点，避免每步都重复询问。
- [ ] 最终视频标记为主交付，人物图、透明图标和报告按用途展示；中间生成完成不能显示为整项需求已交付。

#### 局部失败、恢复与授权

- [ ] 人物图不合格时阻止视频提交；视频失败时复用已验收人物图和图标；图标失败时保留视频；叠加位置错误时只修复合成和受影响的后续检查。
- [ ] 上游图片换版本后，使引用该版本的视频及其依赖结果失效，保留无依赖的图标分支；失效处理不自动授予外部重新生成权限。
- [ ] 区分查询重试、结果重新下载和重新生成；外部重新生成遵守已明确授权范围。当前自动修复仅支持本地命令，不能把未来的外部重生成策略描述为已具备。
- [ ] 增加完整链路测试：两次外部任务的不同中断窗口、版本变更、部分失败、独立分支结果复用、取消传播和最终交付判定。
- [ ] 用户进度按业务步骤和实际阶段展示，例如“人物图已验收／视频等待外部结果／图标已验收／合成待执行”；无上游真实进度时只显示状态与耗时。

调度层继续使用 agent 与 workflow；不因为模型种类增加就创建新的顶层任务类型，也不额外套用 manual 任务。此案例的服务接入与跨步骤引用均为待实现。

| 验收类型 Acceptance.kind | 拆分职责 | 分开对象、检查方法、程序/Agent/用户判断方式，以及必须通过或仅提示的处理要求 |
| Agent 运行目的 review/diagnose/final | 当前基本足够 | 真正接入依赖图修改时再设计 replan 等目的，不预先枚举所有业务动作 |
| 失败策略 pause/diagnose | 需完善 | 统一错误分类、重试、安全恢复、诊断升级和最终处置；明确当前 diagnose 不覆盖所有外部失败 |
| Agent 决定 pass/repair/needs_user/stop | 补语义与载荷 | 明确无法判断、重新规划、终止与阻塞的差别，不能只增加名字 |
| 质量操作 approve/reject/repair | 保留质量职责 | 澄清、选项选择、外部调用授权和计划变更通过独立用户决策协议处理 |
| 工作流命令 validate/submit/status/decision | 当前基本足够 | 脚本预检查与版本修订另定受限协议，不开放任意修改运行中任务的接口 |
| 控制命令 status/cancel/resume | 基础足够 | 按实际需求定义主动暂停；resume 不兼任重试、外部重生成或重新规划 |

#### 权限、操作与验收的具体补项

- [ ] 权限配置明确只读输入、预览目录、新修复脚本目录、步骤输出目录、工具访问和 GPU/模型挂载；不得由 Agent 自选更高权限，也不为每个模型新增沙箱模式。
- [ ] 优先接入纯文生图、参考图生成视频、持久化转写和已有分割/精修/OCR/擦除/局部编辑能力；配音、音乐生成、视频延长和多镜头生成等按后续实际需求引入，不在当前范围内预先宣称支持。
- [ ] 操作 ID 表达业务意图，模型/服务商/环境版本作为实现配置；明确有输入图的编辑与无需输入图的生成不能共用含糊的输入契约。
- [ ] 验收检查器按需扩展透明通道与透明区域、帧率/解码/轨道/时长容差、结构化 JSON 报告、字幕时间范围和受限自定义检查。
- [ ] 必须通过的验收与仅供复核的信号分开；内容验收记录证据及覆盖范围，证据不足不能当作通过。

#### 失败分类与用户决策

- [ ] 建立可执行的错误分类：临时网络/限流/资源不足、参数或代码错误、环境缺失、质量不符、授权或预算不足、外部提交未知；由服务端能力契约决定可否重试和如何升级处理。
- [ ] 将“结果不合格”和“证据不足、无法判断”区分；后者可作为 needs_user 原因或独立结论，具体形式与状态机一起设计。
- [ ] 明确 stop 的语义：当前实现进入 paused；若表示不再继续，应有对应终态，若表示可恢复阻塞则应更准确命名，不能让文案与执行行为相反。
- [ ] 用户决策至少区分质量确认、参数澄清、候选选择、外部重生成授权、计划变更确认。每个请求绑定目标、版本、可选答案及允许的后续动作。
- [ ] 质量 approve 不能隐式授权收费调用；重新生成、修改验收标准或变更计划须核对对应授权范围，不能由 resume 或通用“确认”按钮代替。

#### 九套状态的补齐原则

- [ ] 对话轮：优先补等待/阻塞原因，而非为每个原因新增状态。
- [ ] manual 任务：将计算与外部等待分阶段持久化，和占槽策略一致。
- [ ] 工作流：区分可恢复阻塞、等待用户和终止，明确失败结束语义。
- [ ] 步骤：区分待依赖、待资源、待重试等原因；仅在确有对应行为时新增终态或跳过状态。未实现条件分支前不凭 skipped 枚举宣称支持条件工作流。
- [ ] 验收请求：任务取消、预算耗尽、恢复次数用完后应明确关闭或失效，不能长期保留 running/pending 记录。
- [ ] 执行尝试：分开执行结果与退出原因，统一正常结束、异常中断与租约过期的记录。
- [ ] 外部调用：统一提交中、已确认、提交未知与最终结果的表达和恢复入口。
- [ ] 本地清理：现有状态基本足够，重点验证记录与真实资源一致。
- [ ] 外部清理：明确取消成功、无法确认及上游不支持取消的语义，不能把本地停止视为取消成功。

#### 输入输出契约与实施顺序

- [ ] 明确输入引用来源：上传素材、前置步骤已验收输出、参数/配置；跨步骤引用绑定角色与版本，不只传文件名。
- [ ] 明确业务输出角色：主图、前景、蒙版、视频、字幕、报告、预览等；验收通过、可供下游使用、最终交付和主展示分别表达。
- [ ] 先稳定调度与对话概念，再确定权限/执行/验收契约，随后接入操作与产物引用、失败与用户决策、等待原因；迁移和旧任务恢复测试随接口设计同步安排。
- [ ] 每个新增取值必须有完整的输入校验、权限、调度、状态转换、恢复、取消、预算和界面行为；只添加枚举不算能力完成。

## 待优化：API 外部依赖异步化与线程池隔离

用户于 2026-11-02 先确认记录，随后明确授权“先优化，然后再做完整测试”。本项已进入实施与验证；设计、逐项状态和证据见 [API 隔离设计](api-isolation-design.md)。下述“当前事实”保留改造前问题背景，不代表新版运行状态；完成定向测试不等于已部署。

### 当前事实与风险

- API 上传检查、图片规范化和缩略图请求会经 `media_isolation.run` 调用 `media_service.request`，通过 Unix Socket 和 `SCM_RIGHTS` 传递已打开的文件描述符；路径、数据库和对象存储凭据不进入解码服务。
- `media_service` 只接受 image、normalize、probe、thumbnail 四类固定操作，并在隔离环境中执行 FFmpeg、ffprobe 或图片检查。独立服务首先是安全边界、故障边界和资源边界。
- 当前 API 客户端采用“一次请求一个连接”的阻塞式 send/recv；调用线程在解码完成、失败或超时前持续占用。`media_service` 的两个执行槽只能限制实际解码并发，不能为 API 公共线程池提供隔离。
- 缩略图路径还使用阻塞式 `BoundedSemaphore(1)`。媒体请求集中到达时，等待信号量或解码结果的请求可能占满 FastAPI/AnyIO 公共工作线程，使不依赖媒体的普通同步接口也无法取得线程。
- 两个 API 实例和 Nginx `least_conn` 只能分散或推迟饱和；若 A、B 的公共线程池同时被媒体请求占满，用户可能看到整体 API 无响应。纯异步入口可能仍可运行，但不能据此宣称业务服务可用。

此风险优先级定为 **P0 可用性**。不能用 `media_service` 已限制并发、已有 Socket 超时或部署了两个 API 实例作为风险已消除的依据。

### 2026-11-02 SDK 核验与选型结论

本次只核验当前项目实际使用的 SDK、协议和运行环境，不引入依赖或修改实现。判断标准不是“依赖服务端容量是否足够”，而是 API 进程能否在等待依赖时释放事件循环与公共工作线程。异步调用、连接池和协议多路复用是不同能力，文档中不得混称。

| 依赖 | 当前实现与本机版本 | 官方/协议能力 | 后续选型 |
| --- | --- | --- | --- |
| PostgreSQL | `psycopg 3.3.6`；`AsyncConnection` 可用；`psycopg_pool` 未安装；当前 `Store` 每次同步连接并执行 | Psycopg 支持原生 asyncio 和异步连接池，但官方明确同一连接上的查询及结果读取仍串行；pipeline 也不是多个独立事务在一个连接上并发返回 | 当前同步 `Store` 先进入独立、有界数据库线程池；若以后整体改为 async Store，再增加 `psycopg[pool]` 并使用 `AsyncConnectionPool`。不得把单连接描述成可并发多路复用 |
| Redis | `redis 6.4.0`；`redis.asyncio` 已安装；当前 SSE 通过线程调用同步 `XREAD` | redis-py 提供原生 asyncio API和异步连接池，命令可直接 `await`，不需要占用 API 同步线程 | SSE 读取优先改用 `redis.asyncio`；保留数据库降级路径、连接关闭和重连退避。无需为 Redis 新增隔离线程池 |
| BOSS / S3 | `boto3 1.43.123`、`botocore 1.43.123`；当前同步 put/get/delete，并在客户端加解密、哈希和落盘 | 生产级 Boto3 官方接口同步阻塞；AWS 原生异步 Python SDK v4 仍为实验版，官方不建议生产使用；本机未安装 aiobotocore/aioboto3 | 保留生产级 Boto3，放入独立、有界存储线程池；复用客户端 HTTP 连接池。客户端 AES-GCM、SHA-256、临时文件和 fsync 也归该池，不能只隔离网络调用 |

| Observer | API 通过同步 `urllib` 调用本机 18768，超时 2 秒 | 当前客户端无 asyncio；Observer 是普通本机 HTTP 请求，不具备需依赖 HTTP/2 的双向多路复用场景 | 先放入独立诊断线程池；若后续把 `httpx` 加入生产 `web` 依赖，可改为共享 `AsyncClient` 和连接池 |
| 控制意图分类 | 同步 `requests`，最多 2 个槽，调用超时受限 | requests 无原生 asyncio；现有非阻塞槽位获取能限制在途调用，但请求期间仍占 API 线程 | 放入独立控制调用线程池，保留两槽和快速失败；是否迁移异步 HTTP 客户端按实际调用量决定 |

Agent 模型、图片/视频生成、转写和正式媒体处理均在 Executor/工作流中运行，不属于本项 API 外部依赖改造范围。API 本地静态文件、短 JSON 校验和短数据库结果转换也不应为了形式统一全部异步化。

### 统一执行边界

- [ ] API 事件循环只运行短逻辑和原生异步 SDK；任何同步网络、磁盘、加解密、哈希、压缩、FFmpeg 或数据库调用都不得直接进入事件循环。
- [ ] 不建立一个新的“万能外部依赖线程池”。至少分开数据库读取、业务写入、BOSS/文件、媒体解码、诊断、控制调用，并为健康检查和取消保留独立容量。
- [ ] 每个执行池同时配置 worker 上限和等待队列上限；队列满时返回稳定的 `429` 或 `503`、`Retry-After` 和查询编号。线程池默认无界队列不符合要求。
- [ ] API 协程被取消后，如果底层同步 SDK 不能取消，槽位必须等真实调用结束后再释放；不能在后台线程仍运行时提前记为空闲并造成超配。
- [ ] 为每个依赖分别设置连接、获取连接、执行、读取响应和总 deadline；超时后是否已产生远端副作用保持真实状态，不能统一解释为“没有执行”。
- [ ] 记录每个池的 active、queued、rejected、wait_seconds、run_seconds、timeout 和 error；记录原生异步客户端的连接池占用与重连。指标不得包含凭据、对象 key 或用户内容。
- [ ] 缩小 `mutation_lock` 和数据库事务范围。BOSS 上传下载、媒体解码、哈希、加解密、`fsync` 和递归目录删除不得在全局应用锁或 PostgreSQL advisory transaction lock 内等待。

### 建议实施顺序

1. 先补依赖调用耗时、公共线程池占用、排队和拒绝指标，建立双 API 当前基线。
2. Redis SSE 改用现有 `redis.asyncio`，去掉同步 `XREAD` 对线程的占用，验证断线后数据库降级。
3. 建立有界隔离执行器，将 BOSS/文件、Media Service、Observer、控制分类和当前同步 PostgreSQL 分池；同步 FastAPI 路由需由协程等待专用池，不能只是在线程池内再等待另一个线程池。
4. 将长 I/O 移出 `mutation_lock` 和数据库事务，改为“短事务预留 → 无锁执行外部 I/O → 短事务发布”，处理并发删除、取消和版本变化。
5. 压测后再决定是否引入 Psycopg `AsyncConnectionPool`、生产级异步 HTTP 客户端或 Media Service 自定义多路复用协议；不能在缺少收益证据时同时重写所有传输。

后续用户已授权实施、完整测试及整合发布。各步骤仍需分别评审与定向验证，再冻结全部代码做完整测试；Media Service 长连接协议保留为压测驱动的后续选项，不在本期为形式上的异步而重写。

### Media Service 短期方案：隔离线程池并限制排队

- [ ] 将触发媒体解码的 API 调用链改为 `async def`，在进入阻塞客户端前使用异步准入控制，不先占用 FastAPI 公共工作线程排队。
- [ ] 为现有阻塞式 Unix Socket 客户端建立独立、固定大小的媒体线程池；该线程池不得与普通同步 API 共用。实际执行并发与 `media_service` 槽位保持一致或按实测配置。
- [ ] 同时限制执行数和等待队列长度。队列满时快速返回稳定的 `429` 或 `503`、查询编号及可重试语义，不允许无界排队。
- [ ] 区分准入等待、Socket 连接、解码执行和响应读取的期限；客户端断开、请求取消或 API 排空时停止等待并安全关闭本端 FD/Socket，不能误报解码已取消。
- [ ] 普通接口保留独立容量；媒体服务故障、超时、过载或持续恶意文件输入不得耗尽 API 公共线程池、文件描述符或内存。
- [ ] 增加媒体执行中、排队中、拒绝数、等待时间、执行时间、超时、断连和线程池占用指标，并在诊断中区分 API 排队与解码服务繁忙。

短期方案不要求立即修改 FD-only 安全协议，也不以增加解码并发提高吞吐；目标是建立背压并隔离故障域。

### Media Service 长期方案：异步多路复用客户端

- [ ] 评估在每个 API 实例与配套 `media_service` 之间使用持久 Unix Socket，以 `request_id + SCM_RIGHTS FD` 提交请求，并通过 Future/Promise 唤醒对应协程。
- [ ] 协议必须支持并发请求、响应乱序、单请求期限与取消意图、服务重启、连接断开、重新建连、背压和有界响应；不能因长连接而放宽固定操作白名单。
- [ ] 明确 FD 所有权和关闭时机：发送成功、发送失败、服务接收、请求取消、连接中断和服务崩溃均不得泄漏或错误复用描述符。
- [ ] 多路复用只用于避免 API 同步等待和重复建连，不扩大解码槽位；服务端仍按固定工作池执行，并保持调用者 UID、文件类型、归属、大小、链接数、输出大小及无网络隔离校验。
- [ ] 若短期独立线程池已满足容量和复杂度要求，应依据压测数据决定是否实施长连接协议，不能仅为“异步”重写安全边界。

### 通用验收要求

- [ ] 分别注入 PostgreSQL 慢连接/慢查询、BOSS 慢上传/慢下载、Redis 断连、Observer 超时、控制分类超时和 Media Service 卡住；一种依赖异常不得占满其他依赖的执行池。
- [ ] 在所有外部依赖达到配置并发和排队上限时，静态页面、基础健康检查及不依赖该故障源的只读接口仍可响应；取消和诊断必须有预留容量，不能与普通业务共用最后一个槽位。
- [ ] 验证队列满时快速失败，响应包含稳定错误码、查询编号和重试语义；不能出现请求已返回过载但后台任务仍被无界提交的情况。
- [ ] 客户端断开和协程取消后，原生异步调用正确取消或收尾；无法取消的同步 SDK 继续占用自己的槽位直至真实结束，不提前复用连接、线程或 FD。
- [ ] 对比改造前后的 API 公共线程池占用、事件循环延迟、依赖连接数、吞吐和尾延迟；只有普通业务可用性改善且依赖侧没有无界并发，才算达到目标。
- [ ] 双 API 分别和同时压测；验证一个实例的池饱和不会污染另一个实例状态，同时确认共享 PostgreSQL、Redis 和 BOSS 的全局并发仍受控。

### Media Service 专项验收

- [ ] 在单个和两个 API 实例上分别持续发起超过媒体执行及排队容量的上传、probe、normalize 和 thumbnail 请求；超额请求应有界失败，不得无限等待。
