# 可观测性技术设计与实施要求

记录日期：2026-10-31。来源：用户明确要求“可观测性一定要好”。优先级：P0。状态：本专项已实现、完成自测并部署；24 项按 [检查表](observability-checklist.md)验收，详细边界与证据见 [实施报告](observability-implementation-report.md)。

## 完成目标

运维只拿到一个任务 ID 或页面错误编号，即可查询完整时间线，回答：谁在什么版本的哪个节点执行了哪一步、当前为何等待、最后一次有效进展是什么、失败在哪里、已保留哪些成果、取消和清理是否完成、下一步可以安全做什么。新接入的业务能力必须继承这套能力，不允许每个业务各自拼日志。

诊断必须区分已证实事实、可能原因和证据缺失。没有足够证据时明确显示未知，不将超时推断为上游失败，不将断开请求推断为上游取消成功。查询和导出只读，不自动重试、重提收费请求或修改任务。

## 当前基础与缺口

已有 journal 服务日志、共享数据库任务事件、执行尝试与租约、上游调用记录、取消/清理记录及部分阶段耗时。现场已能追踪旧尝试过期、新节点接管和最终交付。

缺少统一结构化日志、HTTP 到后台任务的关联、覆盖所有异常路径的脱敏堆栈、单任务诊断入口、集中检索、明确保留策略及告警闭环。现有部分异常仅保存摘要，部分容错路径静默忽略异常；必须逐项审查，不可只在顶层增加日志声明完成。

## 1. 标识与上下文

- 建立统一日志字段：UTC 时间、级别、事件名、服务/实例、节点/worker、部署版本、request_id、trace_id、span_id、project_id、task_id、workflow_id、step_id、revision、attempt_id、generation、operation、implementation/version、阶段、耗时、结果、error_code。按适用范围填写；无任务的请求、API 启动和数据库故障也能记录。
- HTTP 请求分配 request_id 并在响应返回；页面报错显示可复制编号。客户端传入的关联信息必须校验，不能用它授权或混淆租户。取消请求、验收请求和外部提交的业务 ID 保留独立语义，不能混用为 HTTP request_id。
- task_id 是长程任务的稳定查询键；每次领取、重试、接管、轮询建立独立 span，并通过持久化上下文关联。并行分支、后续用户取消请求使用关联链接，不伪造单线程父子关系，不让一个 span 挂起数小时等待上游。
- 上游业务任务 ID 与供应商 HTTP 请求 ID 分开保存；供应商不返回请求 ID 时标为缺失。沙箱、子进程、线程、进程间网关和独立 watchdog 的上下文显式传递并隔离，不能串到其他任务。

## 2. 事件、日志与错误

- 统一 JSON 日志输出；覆盖入口、调度决策、领取、准备、执行、上游提交/查询/收取、验收、发布、恢复、取消和清理。对重试、接管和拒绝旧代次提交记录原因及关联对象。
- 状态变更的持久化审计与控制事务保持一致，明确区分意图、执行开始、已提交成功和失败；不能在事务回滚后留下“已成功”的唯一诊断证据。观测数据不成为执行授权来源。
- 后台预期控制流（取消、排空、租约丢失）与代码异常分级处理。代码异常保留脱敏堆栈、错误码、阶段、可重试性和因果链；用户侧保留安全摘要和查询编号。审查静默捕获点，保留容错同时输出有界告警或失败计数。
- 子进程记录退出码、信号、超时、OOM/资源限制证据和有界输出；无法证实 OOM 时不能猜测。心跳和成功轮询允许聚合/采样，但故障、状态转换、接管、取消及成果发布必须可追溯。
- 统一脱敏边界，限制字段长度、输出量和嵌套深度，防止日志注入。默认不记录完整提示词、用户素材、字幕、脚本正文、环境变量或供应商请求/响应体；密钥、Cookie、Authorization、签名 URL、加密密钥不得进入日志、指标或诊断包。

## 3. 单任务诊断与用户侧展示

- 提供只读 CLI/API，支持 task_id/request_id 查找并关联任务、步骤修订、尝试、节点、发布版本、事件、上游调用、产物/checkpoint 和两类清理状态；入口命令名在实现时统一确定。
- 默认输出摘要：当前状态、等待原因/持续时间、最近进展、当前执行归属、最近错误、下次查询/重试时间、恢复约束、建议动作及证据链接。再按需展开时间线和详情，避免一开始输出成千上万行。
- 支持按节点、版本、时间窗、operation、错误码检索；提供分页、有界查询、合适索引与 UTC/本地时区展示。跨节点时钟偏差不能误导事件因果顺序，使用数据库事件序号和因果关联辅助排序。
- 用户能区分排队、依赖等待、CPU/GPU 资源等待、上游等待、结果下载、验收、暂停和清理。无供应商进度时显示阶段及已等待时间，不伪造百分比。
- 支持脱敏诊断包，保存版本、时间窗和证据完整性说明。权限至少区分项目所有者和运维；只知道 ID 不获得查看权限。数据库或单节点不可达时尽可能返回已有证据并标记不可达/缺失，不能因诊断查询再次故障而只给空结果。

## 4. 指标、看板与告警

- 统一指标包括：API 请求量/错误率/延迟，队列长度与最老等待时间，各阶段耗时与失败率，重试/接管、节点心跳、CPU/内存/GPU/磁盘占用与配额，上游耗时/失败/轮询、取消响应时间、本地及外部清理积压、数据库/对象存储可用性、遥测丢弃量。
- task_id、request_id、用户 ID、外部任务 ID 等高基数字段仅用于日志/追踪，不作为指标标签。指标标签按服务、阶段、operation、供应商等受控枚举组织；并行尝试累计耗时与任务墙钟耗时分开命名。
- 提供集群、任务、上游和存储四类视图，从告警可跳转到关联日志/任务及操作手册。健康探测区分存活、就绪、依赖可用和业务成功，不以配置存在推断上游正常。
- 配置节点失联、持续 5xx、队列长时间无进展、上游提交未知、清理超期、存储失败、磁盘/日志容量和观测链路失效告警；实现去重、持续时间窗口、恢复通知和维护静默。阈值通过故障注入与负载测试确定并入库/配置，不把长视频正常生成误报为卡死。
- 告警包含影响范围、首次/最近发生时间、版本、关联任务样例和排障入口。真实通知渠道与收件人未配置前，显示“未配置”；测试使用本地接收端，不擅自发送外部消息。

## 5. 部署、留存与故障隔离

- 单机部署先统一结构化 stdout/journal，再由独立采集器汇聚日志、指标和追踪，支持后续跨机部署。采集器复用通用协议（优先 OpenTelemetry/Prometheus 兼容），具体后端在资源评估后确定。
- 明确各类日志/事件/追踪/诊断包的容量、保留天数、轮转和删除规则；任务持久化审计与可采样遥测分开管理。保留策略不得误删活跃任务恢复必需的数据。
- 观测出口使用有界缓冲、超时、重试和背压。采集器不可达、日志磁盘满或遥测数据库写入失败不得阻塞业务、突破资源限制或触发任务重提；同时通过独立本地路径暴露观测降级与丢弃计数。不能吞掉业务数据库故障来伪装成功。
- 将观测组件、健康检查、容量配置和状态展示纳入 deploy.sh 的部署/启停流程；停止、恢复、维护期间仍需能定位故障。新增依赖要评估当前宿主资源并提供回退步骤。

## 实施步骤与发布门槛

1. O1：统一字段、错误模型和脱敏库；补全日志与持久化事件，关联 HTTP、任务、attempt 和上游。
2. O2：实现单任务诊断 CLI/API、权限、诊断包及用户侧错误编号/等待原因。
3. O3：接入指标、采集、检索和看板，配置留存及观测自身的健康状态。
4. O4：完成告警与操作手册，联动部署脚本，进行故障注入和容量/开销验证。

每一步完成静态 review、单元测试及功能测试，记录源代码版本和原始证据。最终逐项对照 [专项检查表](observability-checklist.md)，完成整体回归、部署演练和报告；所有待实现项与检查项通过前不能标为完成。新 operation 接入必须通过相同观测契约测试。

功能验收必须实际演示：只提供任务 ID，值班人员无需手工连接多张表即可找到步骤、节点、错误与安全后续动作；HTTP 500、脚本失败/OOM、同步超时、异步提交未知、worker 强杀接管、数据库/BOSS 故障、取消晚到上游结果及清理失败都有测试证据。外部故障注入使用隔离替身，不重复付费生成。

负载验收记录测试数据量、任务并发、诊断查询 P95、采集延迟、CPU/内存/磁盘和业务耗时增量；设定并验证可接受预算后发布，不能以小样本查询成功证明海量日志下仍方便。诊断结论、分阶段耗时与原始记录必须一致。
